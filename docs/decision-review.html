Decision review: the language choices, read together

A review of the 118 decisions on language-choices.html (L0 to L117), read as one design on 2026-10-17. Each point here is a place where a decision pulls against Astra's goals, carries a risk, or leaves a gap. Each has options, a recommendation and a line for your decision, as on the main page. Counts of "the apps" are of the code being ported: JadeLib, JadeMem, Snips, JadeMail, JadesDomain, JadeNet and JadeGen.

The user's principle, set at R8

Astra being a good, useful language comes before porting Kotlin easily. Porting is done once, perhaps with a few passes after testing, and then costs nothing more. What matters is Astra's speed, stability and readability; the porting question is whether Astra can do what the code does as well or better. Porting effort alone is no reason to choose an option.

The goals they are read against: a scripting language that is fast enough (M6.5 to M14); Kotlin apps ported by translating syntax, not redesigning; no third-party code; no word that is accepted and does nothing; one name for one thing; and astra code.astra always working. The labels say which kind of point each is: goal against a goal, risk a choice that may cause trouble, gap something not yet decided.

Against Astra's goals

R1 suspend and reified: words that do nothing

goalAbout L7 and L55; the rule of L47.

The point. Your rule is that no word is accepted and does nothing: open, final, sealed, public and @Volatile are errors for that reason. suspend breaks it: L7 keeps it "accepted and changes nothing", and L55 keeps it again. Kotlin's reified is in the same place: Astra keeps type arguments when running (L14), so it would mark nothing.

Evidence. The apps write suspend fun 26 times and reified 3 times. The parser accepts suspend today (src/parser.cpp).

Options.

GainLoseRun speed
a. Both errors, saying the word is not needed (any function may wait; type arguments are always kept); if L7's later check that works out which functions may wait is built, suspend can come back then with that meaningThe rule holds without exceptions.29 words deleted when porting.None.
b. suspend given a meaning now: a function marked suspend may wait, and calling it where waiting is impossible (a sort's comparison, a getter, toString()) is a compile error; reified an errorA real check; ported code unchanged.Work in M6.5 that L7 put off; the mark must then be written wherever waiting happens.None.
c. As decided: both accepted, doing nothingNothing to change.Against the rule.None.
Recommendation

(a).

Decided2026-10-17: (b), suspend given a meaning now, with errors that explain. suspend fun marks a function that may wait, setting its task aside; the standard library marks its own calls that do (delay, a channel's send and receive, Job.get, Countdown.await, waitUntil, suspendTask, Thread.sleep). A function that calls one may wait too, and says so: an unmarked function calling a suspend one is a compile error, as in Kotlin, so ported code, marked already, compiles as written. A suspend function may be called from another, and from code that starts its own task or thread to run it: task { }, thread { }, a pool's or queue's submit { }, and the top level of a script. It is refused wherever waiting is impossible, even inside a suspend function: a sort's comparison, a getter or setter, toString, == and hashCode, a generator's block (where only yield waits, L78) and a parallel section. The error says why, and how to call it safely, naming the call and the place: 'fetch' may wait (it is a suspend function), and a getter must give its value at once: whoever reads 'title' would be held up. Call it from a suspend function, or start it in a task and use the result when it is ready: task { fetch() }.then { title = it }; and for an unmarked caller, 'load' calls 'fetch', which may wait, so 'load' may wait too: mark it 'suspend fun load()', or run the call in a task of its own: task { fetch() }. reified is an error saying why it is not needed: type arguments are kept when the program runs (L14), so x is T works in any generic function. Blocking input and output is not marked (the user, the same day, as in Kotlin): reading and writing files, sockets and other programs' streams block the thread they run on, as Java's do, and never set a task aside, so a function that reads a socket needs no suspend and the apps' socket code (about 130 places) ports as written. This changes L99's "sets a task aside" for sockets: a server serves each connection from a thread or a pool's job; a task that reads a socket holds its thread meanwhile. Built in M6.5. Changes L7 (D30) and L99 (D120).

R8 Checked exceptions in callbacks

The point. Kotlin has no checked exceptions, so nothing in the apps declares any. goalAbout L11, L12, L20 and L28, against astra code.astra starting quickly.

The point. A script is compiled each time it is run. Several decisions are analyses over the whole program: which checked exceptions leave each function (L12), which classes reflection can reach (L28), whether a key's hash can change (L11), whether two extend declarations conflict anywhere (L20). Each is cheap alone; together, on a program the size of an app, they may make starting slow.

Options.

GainLoseRun speed
a. A budget, measured: M6.5 sets a target (say, a 20,000-line program compiles in under half a second) and measures it on a ported app; if over, results are kept per file beside the .astc and only changed files are worked out againStarting time stays known and bounded.Work in M6.5 if the budget is missed.None when running; starting faster.
b. Nothing nowNo work.Found late if it is slow.Unknown.
Recommendation

(a).

Decided2026-10-17: (a), a budget, measured, and building only what changed (the user's addition). M6.5 sets three targets, measured on this machine with a release build, first on a 20,000-line program made of the standard library, Jade, the examples and the tests, then on a ported app: a first run, nothing cached, checked and compiled in under half a second; a second run with nothing changed in under 20 ms on top of astra.exe starting; a run after a one-line change inside a function in under 100 ms (both added by the user the same day). Each is a timing test reported at the milestone's checkpoint; one that is missed keeps M6.5 open until the checker or the cache is fixed. To meet it, and so a one-line change never rebuilds everything: (1) Each file is compiled once and kept, keyed by a hash of its text, in a cache of Astra's own (beside astra.exe's per-user data, not beside the scripts). (2) Each declaration has a summary of what others can see of it: its type, the checked exceptions it may throw (L12, worked out), whether it may wait (R1), whether its == and hash are stable (L11), a const's value (R2), an inline function's body (L60). A file is compiled again only if it changed or a summary it uses changed; changing a function's body without changing its summary rebuilds that file alone, and a change that does alter one (a new checked exception, say) rechecks only the files that call it. (3) The standard library and Jade are compiled when astra.exe is built, their summaries carried inside it, so no script's start checks them again. (4) The work that needs the whole program is done on the summaries, not the sources, and the part only a built program needs (leaving out unreachable code and reflection's reach, L28) runs only in astra build; a script run from its source keeps everything. (5) M14's native code compiles each part's C++ separately and links, so its C++ too is rebuilt only where changed. (6) A script's run is kept for the next one (the user's addition): running astra something.astra also keeps the whole compiled program in a cache of this machine's own, so a second run with nothing changed loads it and starts at once, with no reading, checking or compiling. "Nothing changed" is told by each file's size and time, then its hash where those differ, for the script and everything it imports, and by astra.exe's own version; any difference rebuilds only what changed, as above. The cache is the machine's: kept in the user's local data (%LOCALAPPDATA%\Astra\cache on Windows, ~/.cache/astra on Linux), never beside the script or copied with it, so it may hold what suits this processor only (the instructions it has, later M14's native code); another machine builds its own on its first run. Astra's own: no setting to turn on, and deleting it only costs one slower start. How the cache is kept (the user, the same day): two kinds of entry, one per source file (its compiled code and its declarations' summaries, keyed by path, size, time, hash and astra.exe's version) and one per program (the linked program, keyed by the script and the keys of everything it imports). Entries are written after the program has started, each to a temporary file renamed into place, so two runs at once see a whole entry or none; a damaged or unreadable entry counts as missing and is rebuilt, so the cache can never stop a script. A file touched but unchanged (same hash) counts as unchanged. Entries of an older astra.exe stop matching and are cleared. A size cap: the cache holds at most 500 MB; past that, the entries used longest ago are removed, oldest first, until it is under, the check made after a run, never delaying one. A script on a read-only drive or a network share caches the same way, the cache being in the user's own folder. Kotlin's, Swift's and Rust's compilers work this way. Built in M6.5, beside the checker. (D145)

R11 Negative indexes and off-by-one

riskAbout L18, against the reasoning of L4 and L111.

The point. A negative index counts from the end, for strings and lists. So items[i - 1] with i at 0 quietly gives the last item, where Kotlin throws. L111 chose an error for pixels outside an image so that "an off-by-one shows at once", and L4 traps overflow for the same reason; negative indexes do the opposite.

Evidence. The apps index with [name - 1] 78 times; every one that can reach 0 is a place where a Kotlin exception becomes a wrong value.

a. Recommendation

(a).

Decided2026-10-17: (d), ^k counts from the end, and no index is negative. In an index, ^k means size - k, for lists, strings and anything else indexed by position: items[^1] is the last item, items[^2] the one before, items[^k] with k worked out when running, and items[^1] = x sets it. It counts from 1, as C#'s does, so ^0 is an error, as is a k past the start. ^ before an index cannot be confused with ^ between two values (bitwise xor). A negative number never counts from the end: items[-1] is a compile error saying to write items[^1], and an index worked out below 0 is an IndexOutOfBoundsException, so an off-by-one such as items[i - 1] at i = 0 fails as in Kotlin instead of giving the last item. last(), lastOrNull(), last { } and lastIndex stay. No cost: ^k compiles to size - k. Slices (the user's addition, D147): a range in an index gives that part, inclusive as .. is everywhere: items[1..] from 1 to the end, items[0..^1] the whole, items[0..^2] all but the last, items[..^2] the same with the start left at 0, items[2..4] items 2, 3 and 4, items[0..<^1] with the end left out; strings and bytes alike (s[1..^2]). Written with .., as Kotlin, C#, Swift and Rust write ranges, not Python's :, which Astra uses for types and in ? :. A slice is a copy (a new open list, L23, string or bytes), as subList and substring gave; splitAt (L76) stays the way to views. Out of range is an error, as an index is, but a slice may end right at the end (items[3..] of three items is empty); a slice that runs backwards (items[3..1]) is an error. subList and substring become errors pointing to it (items.subList(1, 4) is items[1..<4]). One copy of the range, no other cost. ^n in anyone's functions (the user, the same day), as C# does it: ^n makes an Index, a value type of 8 bytes (a number and whether it counts from the end), so it makes no object. A function that takes at : Index accepts 3 and ^1 alike, an int passing as an Index counted from the start, and resolves it against its own length with at.of(size), an int, a position outside 0 to size being an IndexOutOfBoundsException. A parameter typed int does not take ^1 (a compile error: nothing there knows a length to count from). Ranges carry it the same way: a Range may have ^ ends, r.of(size) giving its start and end as ints, so op [](i : Index) and op [](r : Range) give a program's own class thing[^1] and thing[2..^1]; a range with a ^ end cannot be gone through by itself (for i in 0..^1 is a compile error asking for the length: (0..^1).of(xs.size), or xs.indices). For List, String, Bytes and Grid the compiler still makes xs[^k] into size - k directly. R24 No open classes; extend may add stored fields

goalFound while building the checker (M6.5 part one): a class that declares no fields "stays open", so its members cannot be known.

The point. Astra's rule (README, "Fields"): a class that declares fields has exactly those, but one that declares none, nor do the classes above it, stays open: assigning this.x = 1 makes the field, even from outside the class (open.extra = true). Such a class's members exist only when the program runs, so nothing read from it can be checked; its shape is spread through its methods; a misspelled this.nmae silently makes a second field; and its fields can never be reached by position (part 4). Kotlin has nothing like it. Open classes are used for two things: fields made in init without being declared, and data attached to an object from outside.

extend Button {
  var tag : string? = null
  var clicks = 0
}
val b = Button("OK")
b.tag = "confirm"
b.clicks += 1
Decided2026-10-17, the user: open classes go, and extend may add stored fields. Every field is declared, in the header (class Animal(val name : string)) or in the body; assigning a field that is not declared is a compile error wherever it is written. Data attached from outside is declared once as an extension field: extend Button { var tag : string? = null }, lifting L20's "no stored fields". An extension field is a real slot in every instance of the class and its subclasses, kept in an extension area after the declared fields: [declared fields of the class and those above it][extension fields]. The declared part never changes, so code already compiled for the class (the standard library and Jade inside astra.exe, files in the cache, R10) is right for every program; the extension area is laid out per program, in its last step, an ancestor's extension fields before a class's own, so a field added to Button is at the same distance from the area's start in Button and every subclass. Each class records where its area starts (a subclass's starts further on), so reading b.tag is the object's class, its area's start, and a fixed offset: one load more than a declared field, no hashing or search (Kotlin and C# need a table beside the object instead). An object's size comes from its class when it is made, so it includes the area; the program's last step writes, for each class, the setting of its extension fields' initial values, done when an object is made, before init. (Corrected the same day, at the user's question about two programs, one extending a standard class: as first written, an extension changed the class's own layout, which compiled code shared between programs could not follow.) Its name is in reach only where the extend is, by L20's rule, though the slot is in every instance. It needs an initial value, or lateinit, since the class's own initializer does not know it; it is typed and checked like any field. Two extends adding the same name to one class are an error unless identical (L20). Not on value types or data classes, whose size or header is what they are. It costs one slot (8 bytes) in every instance for each extension field in the program, used or not; for a class with millions of instances, a Map keyed by the object is the better tool. For building only what changed (R10), adding one changes nothing compiled for the class: only the files that use the field and the program's last step. Two programs, one extending Button and one not, share the same compiled Jade; each has its own program entry in the cache, and the one without the extension has no extension area. Open classes go in M6.5 part 3, when everything is typed (the README's examples, the tests and the standard library declare their fields); extension fields are built with extend. Changes L20. (D157)
