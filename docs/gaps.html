M6.6 so far: what is left open

The choices made while building M6.6 that are not yet confirmed, and the gaps it left, each with where it is to be dealt with: the first half, parts 1 to 7, and of the second half, part 8's groups as they are built. Written 2026-10-19, and brought up to date after each part since: the gaps they closed are gone from the list. The same items are in gui-plan.md (the M6.6 notes, D162 to D180 and the Open list); the design is in value-lists.html.

Contents

  • Choices to confirm (nineteen from the first half; seven from part 8, group 1)
  • Gaps left (twenty-three)

Choices to confirm

D162The type of items.itemType (part 1)

A new built-in type, Type: a type as the program runs. items.itemType, map.keyType and map.valueType give one (any for a collection made without its type). It prints as written (List<int>), two are == when they are the same type, and x is Type tests for one.

Your choice

D163How the C++ functions' results are checked (part 1)

By a test setting, not on every call. ASTRA_CHECK_NATIVE_RESULTS=1 compiles a check after every call of an external function against its declaration; the suite passes with it, and each checkpoint would run it beside the GC and thread stress settings. The C++ is fixed code, so the suite proves its declarations once, and later parts can then trust them while the program runs. The other way, a check on every call, costs every call of the C++.

Your choice

D164What the check changed in the standard library (part 1)

  • The coerce functions give one of their numbers as it was, so float.coerceIn(Number, Number) and the like now say Number, with forms for all ints and all floats that say int and float. (2.5.coerceIn(0, 1) is the int 1.)
  • A type parameter that the object a call is made on says nothing of (a Map written without type arguments) is unknown, not taken from the arguments: data.get(key, "missing") is no longer typed string? there.
  • Deque.toList builds a List<T> rather than casting its List<T?>, and Set == gives false for a set of other things rather than failing at a cast, now that casts are checked in full.
Your choice

D165The rules of a value type, as built (part 2)

  • value Point(val x : int, val y : int) needs a header whose entries are all fields. It is a data class: printing, ==, copy, coming apart.
  • It may implement interfaces, extends no class, and no class extends it.
  • A field is given its value in the header, where it is declared in the body (one declared there with none is an error), or in the type's init; never again. p.x = 4, and x += 1 in a method, are compile errors saying to make a changed copy, until changing through a place (part 4).
  • === on a value type is a compile error, as a value has no identity; through any it compares contents.
  • A value type cannot hold itself except where that field may be null; the checker reports it.
  • Every core may read a value, since it never changes.
Your choice

D179Jade's geometry as value types: decided (part 7)

You chose on 2026-10-19 to make Jade's Point, Dimension, Insets and Rectangle value types, and Jade's Sizes with them: a component's bounds and the sizes it keeps are inside it, and setSize, translate, setLocation, grow and setBounds are mutating methods. Nothing in Jade relied on sharing one; one val that was translated became a var.

D180Rectangle takes all four numbers (part 7)

A value type is made from its header alone, and Astra has no constructors of other forms, so Rectangle(x, y, width, height) takes all four with no defaults. Java's Rectangle() is Rectangle(0, 0, 0, 0) and Rectangle(w, h) is Rectangle(0, 0, w, h): both are compile errors as written, so that Rectangle(30, 40) cannot quietly mean the corner. Rectangle(other) is other, which is copied wherever it is kept. Point(), Dimension() and Insets() keep their zeros, as in Java.

Your choice

D166Lists of values, as built (part 3)

  • A list is packed when it is given its type (by its literal, by what it is declared as, or at the call of a C++ function that made it): List<int>, List<float>, List<bool>, a value type's list, and the nullable ones of those.
  • Putting in a value the list was not made to hold is an error where it is put in (cannot put a value of type string in a List<int>), which an unchecked cast through List<any> used to allow.
  • A copy of a list (toList, slice, subList, reversed, + of two of one type) keeps its type and how it is kept.
  • sortBy and sortByDescending, for every list, call the selector once per item rather than twice per comparison (a million items sorted in 70 to 130 ms instead of 1.5 s). A selector with side effects sees fewer calls.
Your choice

D167Changing a value through its place (part 4)

  • A var field of a value is changed only through a place that holds the value: a var variable (local, global, or one a lambda holds), a var field of an object, an item of a list, a value's field that is itself a place, or a lambda's parameter (what forEach { it.move() } is given). So p.x = 4, p.x += 1, pts[i].y++, line.to.x = 9.
  • A mutating fun may change this's fields and call the type's other mutating methods, and is called only on a place. mutating on anything but a value type is an error.
  • A variable or field changed this way gets a value of its own first, so val q = p; p.x = 10 leaves q as it was.
  • Every part of pts[next()].x += 1 is worked out once.
Your choice

D168Reading a value where it is (part 4)

  • A value read from a list or another value (pts[i], a loop's item, a lambda's it, a parameter, this) is not copied where the checker shows that nothing which may change a list of its type runs while it is in use, through what the code calls, overrides included. Changing a list means removing, inserting, sorting, setting or replacing items; adding at the end is not, as a reference into a list is by position. A function given as an argument counts as one that may.
  • A loop is judged by its body. If the body gives the item to a variable from outside the loop, the loop is judged by the whole function, as the item might be used after it.
  • A call that may wait counts as one that changes every list, since other code runs meanwhile: a flow that waits in a loop reads each item as it was when the loop came to it.
  • Whatever keeps a value longer than the stack does (a field, a list, a global, a variable a lambda holds, a C++ function) takes a copy.
  • The test setting ASTRA_COPY_READS=1 copies every read; the suite prints the same with it.
Your choice

D169Results built where they go (part 4)

  • pts[i] = f(...), where f gives a value of the list's type, gives f the item as where its result goes. A function that gives a value passes that on to a call whose result it returns, and making a value from its header alone writes its fields there, every argument worked out before any is written.
  • So pts[i] = pts[i].moved(1), pts[i] = Point(...) and pts[i] = pts[i].copy(x = 4) make no copy.
  • list.replaceAll { it.moved() } replaces each item by what the lambda gives, built where the item is.
Your choice

D170Parallel sections over a list of values (part 4)

  • pts.parallelStream() deals each core its own part of the list and hands it the items where they are: forEach { it.move() } changes them there, map and the rest read them there.
  • parallelStream().replaceAll { it.moved() } replaces each item, on every core, built where it is. On a list of anything else it puts what the lambda gave in once every core is done.
  • A core reads and writes only its own part (pts[0] from another core's part is an error saying so), and changes the list itself not at all (sortBy, sortByDescending and replaceAll now count as changing a list, as they should have already). A built-in function given the whole list is refused, but for isEmpty and isNotEmpty.
Your choice

ThreadsNo scan at a thread switch (part 4)

The plan was to replace a thread's references into lists by copies whenever it gives up the lock. Not built, and proposed not to be: a thread gives the lock up only at a call or the end of a loop body, and another thread reordering a list meanwhile is a race, which Astra lets give a wrong answer but never damage anything. A reference into a list is checked against the list's length and its type of item every time it is used, so a race at worst reads or changes another item, as it would with objects. A flow is not a race (other code runs at the points where it waits, by design), and the checker handles it (D168).

Your choice

D171Small values in the value itself (part 5)

  • A value type whose layout is at most 8 bytes and holds no object (value Rgba(val argb : int), value Meters(val m : float), value Flags(var on : bool, var shown : bool)) is kept in the value itself: its fields in the 8 bytes a value has for its contents, its type's number beside them.
  • So in variables, arguments, results, fields, lists and maps it takes no box and allocates nothing. The program sees no difference.
  • C++ functions are given one in a box, as they are given every value of a value type; list.add excepted (D174).
  • Measured: bench/colors_values.astra, 100 frames of a 320 by 240 picture blended from a palette, 24 to 31% faster than in part 4, with no box made where part 4 made 15.4 million.
Your choice

D172Values inside their objects (part 5)

  • A field of a value type larger than 8 bytes, not null, is kept inside its object, after its other slots, laid out when the first object of the class is made.
  • comp.bounds = r copies the value's bytes in; comp.bounds.w = 30 and comp.bounds.origin.move(1) change it there; comp.bounds = Rect(...) and cached = measure() build it there.
  • A field is laid out so when its type is written, or when it is given a value made by its type's name (var cached = Size(0, 0)). A field of an object made before its class's field types exist keeps a box.
Your choice

D173Fields and results read where they are (part 5)

  • Giving a field of a value type another value counts, for D168, as a change to values of that type, as changing a list of them does.
  • A field kept inside its object is read where it is (a reference into the object) where nothing that may change values of its type runs while the read is in use; otherwise it is copied.
  • What a function gives back that it read where it is stays so where the caller is shown to be as safe; a call's result read at once by one of its fields (node.sizes().pref), and a field given back by return, always are. Elsewhere a function gives back a copy.
  • Measured: bench/layout_cached_values.astra, Jade's layout with each component's Sizes kept inside it, makes 1,215 boxes where part 4 made 57,126; its time is 4 to 7% more, from the reads through references (a gap below).
Your choice

D174list.add copies where the item is (part 5)

out.add(p) for an item read where it is, in a loop say, copies its bytes straight into out, with no box made for it on the way: filtering a million points by hand takes 43 ms instead of 65. add(i, item) copies the item first, since the items after i move.

Your choice

D175Generic functions copied per layout: not now (part 5)

Measured on a million points: map 46 ms against 41 written out by hand, sumOf 25 against 23, filter 98 against 43, sortedBy 84. The check that generic code makes costs a few percent. filter's difference comes from copying each item it hands to its lambda, since the lambda might change the list; inline functions (D59, the second half) remove that, and copies per layout would not. Proposed: copies per layout wait until a measurement asks for them.

Your choice

D176A number's conversions and Math's functions as instructions (part 6)

x.toInt(), toLong(), toFloat(), toDouble(), roundToInt(), roundToLong(), isNaN(), isInfinite(), isFinite(), and Math.sqrt, floor, ceil, round, abs, and min and max of two ints or two floats, where the checker knows the call is the standard library's, are one instruction each, giving what the library's own gives, errors included. Drawing a million particles a frame is 34 to 40% faster.

Your choice

D177Fields kept as their payload alone (part 6)

  • An int, a float or a bool field whose type is known (written, or worked out from what it is first given), and not null, is kept in its object as its 8 bytes of contents alone, before the object's slots, at the same place in every object of its class. An object of three float fields takes 72 bytes in place of 96: a million of them, 112 MB at most against 142.
  • A val, and a field an init must set, has a bit saying whether it has been given a value, so that giving a val a second value, and an init that leaves one unset, are still errors.
  • Any other payload reads as 0, 0.0 or false before it is first given a value, where a slot read as an error. (Only code that reads a field before the line that gives it its value sees the difference.)
  • Field reads and writes are as fast as before, with Clang and with MSVC.
Your choice

D149Values in variables, in M6.7 (D178)

Values of up to 32 bytes kept in consecutive slots of a frame (D149) need the same change to how a frame's slots are laid out as frame slots that keep only a payload. You decided on 2026-10-19 (D178) that those, with instructions chosen by type for arithmetic, come with M6.7's rewritten loop. Until then a value larger than 8 bytes in a variable, an argument or a result is a box.

SizeThe largest value type (from value-lists.html)

Decided "any size, up to 64 KB". Offered on 2026-10-18 and not yet answered: "any size, with a copy on read past 64 KB". The limit comes only from the 16-bit offset in a reference into a list item, and only fields kept in place count towards it.

Your choice

8.1aA byte becomes an int by toInt() (part 8, group 1)

D19 says byte arithmetic gives an int and an int becomes a byte by toByte(); it does not say whether a byte goes where an int is asked for. As built, it does not: b.toInt(), as an int goes where a float is asked for only by toFloat(), and as in Kotlin. Comparing (b < 255, b == 200) and arithmetic (b + 1, an int) take a byte and an int together. An int literal that fits, or arithmetic on literals, is a byte where a byte goes; a name, even a constant's, is the int it is, as in Kotlin (val n = 5; val b : byte = n is an error).

Your choice

8.1bWhere a char goes for a string (part 8, group 1)

A char goes where a string is asked for only where Kotlin has a form taking a Char: split(','), indexOf('x'), lastIndexOf, contains, startsWith, endsWith, replace('a', 'b'), padStart(n, '0'), padEnd. Elsewhere it is an error saying a string is wanted ("$c" or c.toString() makes one). So a Map<string, V> indexed by a char is a compile error, though when running 'c' and "c" are one key, as a Map<any, V> shows (D25). The other way would be a char taken wherever a string is, made one as it is passed.

Your choice

8.1cA char's upper() and lower() give a char (part 8, group 1)

D74 keeps upper and lower over uppercase and lowercase; on a char each gives a char, the letter in the other case where that is one character, the char itself otherwise. Kotlin's Char.uppercase() gives a string (for ß, "SS") and its uppercaseChar() a char; ported replaceFirstChar { it.uppercase() } becomes { it.upper() }. A string keeps uppercase() and lowercase() beside upper() and lower() until D74 is built.

Your choice

8.1dThe UTF-8 a string is made from is not kept (part 8, group 1)

D20: a string's UTF-8 form is made when first asked for and kept. As Python does, a string made from UTF-8 (read from a file, joined by C++ code) keeps only its characters, at 1, 2 or 4 bytes each, and makes its UTF-8 again when C++ code first asks for it: Latin-1 text then takes a byte a character, not UTF-8's two for é. ASCII text is its own UTF-8, so the question is only for other text. Keeping the UTF-8 it came from would save that pass and cost the memory of both forms.

Your choice

8.1eThe byte order of Bytes' numbers (part 8, group 1)

L0 gives int16(at), int32(at), float32(at), uint16(at), uint32(at) and their put forms "with a byte order". Built as a flag, bigEndian = false by default: buffer.uint32(4, bigEndian = true), buffer.putInt16(0, -2). The other way would be an enum, ByteOrder.big.

Your choice

8.1fwrap32() beside toInt32Wrapped() (part 8, group 1)

D148 names both, and they give the same: the low 32 bits as a signed number. Both are built; one name for each thing (D74) would keep one, wrap32() for the hashing it is meant for, or toInt32Wrapped() for its family.

Your choice

8.1gWhat hash(a, b, ...) combines (part 8, group 1)

Java's Objects.hash rule, 31 * h + hash of each, wrapping at 32 bits, over Astra's own hash of each value (the one map keys use: by contents for strings, lists, data classes and values). A class's own hashCode is not called when running yet; when it is (D26, group 2), hash calls it for a value whose class has one.

Your choice
