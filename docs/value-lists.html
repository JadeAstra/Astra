Lists of values: compact storage

How a list whose items are values (numbers, characters, bytes, booleans and value types) keeps them one after another in memory: a million points in 16 MB instead of about 190, read without allocating, with every list operation and nothing new for a program to choose. Decided 2026-10-14 to be built in M6.6 (L1 and L2 in language-choices.html), with the questions of section 18 decided on 2026-10-18.

1. What it is for

Today a Point(1, 2) is an object of about 170 bytes in two allocations, and a list of a million takes about 190 MB and a million entries for the collector. A list<Point> of value-type points should be:

  • Compact: 16 bytes an item, one after another, as a C array holds them.
  • Free to read: pts[i].x, for p in pts and draw(pts[i]) make nothing.
  • A whole list: add, insert, removeAt, pts[i] = q, sort, clear and every other list function work.
  • Nothing to choose: the program writes list<Point>; that its items are values is what makes it compact.
  • Plain to reason about: what the program reads from it is a value; keeping it keeps a copy, which nothing done to the list afterwards can change.

2. Lists of values and lists of objects

Decided2026-10-14: one sequence type, the list, stored by what its items are. An earlier draft had a separate pack<T>; it is merged into the list.
  • A list of a class (list<Component>) holds references to its objects, exactly as today: an item read from it is the object itself.
  • A list of a value type (list<int>, list<float>, list<char>, list<byte>, list<bool>, list<Point> for a value Point) holds its values one after another, each at its own width. bytes is list<byte>.
  • A list of a type that may hold anything (list<any>, list<number>) holds 16-byte values as today, since each item has to say what it is. A list of a nullable value type (list<int?>, list<Point?>) holds its values packed as the value type's list does, with a bit per item for null (section 18).

Why this is safe. Packing a list of objects would change what programs mean: a kept item would be a copy, not the same object. A value has no identity (=== is refused), so a copy cannot be told from the original, and packed and boxed storage of values differ only in speed and memory. Value types are new, so no existing program changes meaning.

What others do. C#'s List<struct>, Swift's [Struct], Rust's Vec<T> and Go's []T all store value items inline, with no separate packed type. Kotlin and Java, without value types, add IntArray and its kind beside their lists.

Which kind of type to make. Since a value is copied where an object is shared, the author of a type decides: value for small things that are what they contain (a point, a colour, a size), class for things with identity or of large size that are kept and reordered a great deal (section 15). C#'s advice is the same.

3. What it needs first

  • Value types (L2), written value Point(var x : int, var y : int). No identity, == by contents, never changed where anyone else can see it: a var field changes only through the place that holds the value (section 8). They may hold strings and objects. That is what lets a value be copied, or read in place, without anyone being able to tell the difference.
  • A fixed layout per value type, worked out when compiling: each field at a known offset and width (int and float 8 bytes, char 4, byte and bool 1, a reference 8, a nested value type its own size), aligned to its width. Point is 16 bytes; Rectangle(x, y, width, height) 32.
  • Item types kept when running (decided in 5.7), so a list knows its layout.
  • Static types (M6.5), so the compiler knows where an item is read and what becomes of it (section 6).

4. Values outside lists

Decided2026-10-14: all three ways below.

A value that is not in a list of values is kept in one of three ways, whichever its type and place allow. The program sees no difference between them.

In a box. One small allocation with a header (its type) and its fields in the fixed layout, without the field table objects have today. A Point box is about 32 bytes. A box never changes, so it can be shared: val b = a copies the reference to the box, not the fields. The general case: any value, kept anywhere.

Small values in place. A value type of at most 8 bytes is kept in the value slot itself, with no box: its fields in the slot's 8-byte payload, its type's number in the spare bytes beside the kind. With L0's types, that is a value type of one int, float or char (a Color as its ARGB number, an id, a unit), or of up to eight bytes and bools. Such a value costs nothing to make or keep, wherever it is. Point, Dimension and Rectangle are too big and use the other two ways.

Inside their object. A field whose type is a value type holds the value's fields within the object, in its fixed layout: a Component's bounds is 32 bytes of the component. It works as a list of one item:

  • Reading comp.bounds gives a reference into the object (the same kind of value as a reference into a list: the object, and an offset in the spare bytes) where the compiler can show the field does not change while the reference exists, by the rules of section 6; the compiler works out which fields of which classes every function may assign. Otherwise a box with a copy.
  • comp.bounds = r copies the fields into the object; comp.bounds.x = 5 writes one field (section 8); a function returning a Rectangle into comp.bounds builds it there (section 7).
  • The collector follows the object's layout into the value, for the references it holds. Threads and parallel sections follow the object's own rules, and the scan at thread switches covers references into objects too.

So a value is, when the program runs, a box, a value in place, a reference into a list, or a reference into an object. Reading one of its fields checks which (one test, two branches) and reads at the field's offset.

5. A list in memory

A list is one object: its item type, its size, its capacity, and one block of memory with room for capacity items, the first size of them in use. What an item takes in the block follows from the item type:

  • A class: an 8-byte reference.
  • A value type: its own size, from 1 byte (byte, bool) and 4 (char) to 8 (int, float) and as many as its fields need (Point 16, Ball 48).
  • any, number, a nullable class: a 16-byte value, as every list item is today.
  • A nullable value type: the value type's own size, as above, and a bit per item for null, kept beside the items (section 18).

Nothing else: no index, no bits, nothing for the collector beyond the block and, for items holding references, the map of where they are. A list grows by moving to a block twice as large.

6. Reading an item: in place or a copy

Reading an item of a list of values gives either a reference into the list (a value of a new kind: its payload points to the list, its spare bytes hold the item's position and an offset within it) or a box with a copy. Items of 8 bytes or less are simply copied out, as numbers are today, and need neither. Which of the two is the compiler's choice; the program sees a value either way.

A reference into the list is used only where the list cannot change while the reference exists. Everywhere else a copy is made:

  • Within an expression: pts[i].x, total += pts[i].y, pts[i] = pts[i].moved(dt) (the read is finished before the write), pts[i] == q. In place.
  • Passed to a parameter that does not keep it: the compiler sees the whole program, so it works out for every function which parameters it only reads: never stored in a field or a list, never returned, never captured in a lambda, passed on only to parameters that do not keep either. A method that may be overridden counts only if all its versions agree; a call through a function value only if the lambda is known. draw(pts[i]), where draw only reads p.x and p.y, is in place.
  • In a local that goes nowhere: val p = pts[i], used only that way, with nothing that might change a list of Points while p is alive. The compiler works out for every function whether it may change a list of a given item type, directly or through what it calls. In place.
  • Anything else (stored in a field or a list, returned, captured, passed to a parameter that keeps, alive across something that may change the list, or the compiler cannot tell): a copy in a box.

The analysis only ever errs towards a copy, which costs a small allocation and is never wrong. A reference into a list only ever lives on a thread's stack, never in the heap: storing a value anywhere in the heap stores a box, so no object can keep a large list alive through one small value.

7. Making new values where they go

Decided2026-10-14: both rules below, (a) and (b).

A value of more than 8 bytes does not fit in a value slot, so a function returning one, as moved returns a Ball (section 14), would have to put its result in a box: an allocation per call. Two rules keep new values out of boxes.

(b) Stores of a new value. When what is stored into an item (pts[i] = ..., pts.add(...), pts.insert(i, ...)) is a constructor call, Ball(...), or a copy, pts[i].copy(x = 5), the compiler writes the fields straight into the item. All the arguments are worked out first, so a new value may be made from the old one in the same place.

(a) Results built where they go. A function that returns a value type is given a hidden argument: where its result goes. The caller chooses:

  • An item of a list, for balls[i] = it.moved(...). Given as the list and the position, not as an address, and found only when the result is written, so that the block moving (the list growing) cannot leave it pointing at freed memory; the position is checked against the size then. Used only where the function does not change lists of that item type (section 6); otherwise the result goes to the thread's scratch space and is copied into the item after the call.
  • A box, when the result is kept. The caller makes it and passes it.
  • The thread's scratch space, when the result is used and dropped within an expression: a small stack of result areas per thread, taken before the call and given back after the use.

Inside the function the destination is written only by return, after everything in the returned expression is worked out, so balls[i] = balls[i].moved(...) reads all of the old ball before writing any of the new. Constructors and value types nested in others work the same way. C++ and Swift return large values like this (return value optimisation; indirect results).

8. Changing a value through its place

Decided2026-10-14: the four rules for assigning a field, and mutating methods.

A value is never changed where someone else can see it, but a place holding one (a var, a var field, an item of a list) can be given a new value with one field different, written as an assignment to the field, as Swift does.

Assigning a field. pts[i].x = 4 means pts[i] = pts[i].copy(x = 4), under four rules:

  1. Only fields declared var in the value type: value Point(var x : int, var y : int) allows it; with val x it is an error.
  2. Only through a place: pts[i].x = 4; p.x = 4 for a var p; obj.pos.x = 4 for a var field; nested values, rects[i].topLeft.x = 4. On a val or a temporary (f().x = 4) it is an error.
  3. Each part worked out once: in pts[next()].x += 1, next() is called once.
  4. In a list of values, or inside an object, it writes that one field where the value is: pts[i].x += dx is a load and a store. A value in a box gets a new box with the field changed.

mutating methods. A method marked mutating may assign the value's var fields. Called on a place, it works on the value there, and the place then holds the result:

  • On an item of a list of values, or a value inside an object, this is the value where it is: its assignments are written straight there, nothing copied.
  • On a var holding a box, the method works on a copy in the scratch space, written back to the place when it returns.
  • Calling one on a val or a temporary is a compile error. Inside it, this may not be kept (stored, returned, captured); it may call other mutating methods of the same value.
  • A lambda's it is a place when a list of values hands it its own item and the lambda keeps nothing: pts.forEach { it.move(...) }, in a parallel section too, changes each item in place. Where it is a copy (the lambda keeps it), calling a mutating method on it is a compile error that says the change would be lost.

For the reader of a program: var q = p; q.x = 5 leaves p as it was, where with objects both would change. Turning a class into a value type changes what such code means without an error; a type should be a value type only when that is what it is.

9. Each operation

Nothing outside a list of values points at an item for longer than the compiler has allowed, so every operation works on the items directly:

  • pts[i] = v: copies v's fields into item i. add, insert, removeAt, clear: as on any list, moving items within the block.
  • Sorting large items through their positions. For items over 32 bytes, sort, sortBy and their kin first sort a list of positions, 4-byte numbers, with the same comparisons, then rearrange the items in one pass that moves each item once: a million 200-byte records move once instead of about twenty times. Automatic; programs see no difference.
  • Inserting and removing in the middle shifts the items after the position, in one memory copy: for a million 200-byte records about 100 MB, some 10 ms, where references would move 8 MB. The same growth as any list, with a larger constant; accepted, as C#, Swift and Rust accept it. (Storing the list in chunks, or section 17, would remove it, at a cost on every read.)
  • for p in pts: walks the block in order; p is in place or a copy by section 6.
  • replaceAll { }: replaces each item with what the lambda gives for it, built in place by section 7.
  • A comparator lambda gets items in place when it keeps nothing, copies otherwise.

10. Generic code

A generic function, fun <T> first(items : list<T>) : T, does not know when compiled how its list is stored. This matters, because map, filter, forEach, sumOf, sort and most of the standard library's list functions are generic.

  • First, a check. Types are kept when running, so a generic function is given T as a hidden argument and knows the item's layout from it. Each access reads the layout and takes a branch that goes the same way for every item of one list. Estimated 1 to 3% in generic list loops; nothing in code whose types are known.
  • Then, copies made per layout. The compiler sees the whole program, so it can make, for a generic function, one copy shared by all classes (references are all alike) and one per value type the program uses it with, as C# does. No check at all, for some size of bytecode and time to compile. Done first for the standard library's list functions, where the check would show; for the program's own generic functions if measurements say so.

11. Threads, flows and parallel sections

The analysis of section 6 looks at what this thread does; another thread could change a list while a reference into it is on this thread's stack, letting a method read x from an old point and y from a new one.

  • Threads and flows: whenever the VM switches away from a thread, or a flow sets itself aside to wait, it replaces every reference into a list or an object on that stack by a box with a copy. One short scan per switch.
  • Parallel sections, by M3.5's rule (a core may change the item it was given and what it makes itself, and may read everything else except another core's items):
    • A list of values being dealt out (pts.parallelStream(), or pts.parallelChunks { } as for bytes today): each core is given a range of positions; within it, it may read the items and change them (assign var fields, call mutating methods, replace them). Reading an item in another core's range is an error, as looking into another core's object is today; changing the list's size or order during the section is an error. The list records the ranges, since its items have no owner field as objects do, and each access inside a section checks the position against them; outside sections nothing is checked.
    • A list of objects is dealt out item by item, as now.
    • Any other list that existed before the section is shared: read by all, changed by none. A list a core makes in the section is its own.
  • Workers: a list of values is sent to another worker as one block of memory.

12. Safety nets

  • Bounds: reading through a reference into a list checks its position against the list's size, so a mistake in the compiler's analysis gives an error, never a read outside the block.
  • A stress setting, beside the thread and collector ones, that makes every read a copy. The test suite runs both ways and must print the same.
  • The shell (what astra starts with no file): code there is compiled one entry at a time, so a class entered later can add an override that earlier code did not know of. In the shell, calls through methods that can be overridden count as keeping.

13. The rest of the language and the VM

  • Equality and hashing go field by field, so a box, a value in place and a reference into a list with the same fields are equal and hash alike; floats compare as == does (-0.0 equals 0.0) and hash to match.
  • is, printing, copy(...), destructuring treat all four forms of a value alike.
  • Nested values: rects[i].topLeft is a reference with an offset inside the item: the spare bytes hold the position (40 bits, a trillion items) and the offset (16 bits, items up to 64 KB).
  • Value types holding references (strings, objects): each value type has a map of the offsets that hold references, which the collector traces in every item and every value inside an object.
  • Built-in functions in C++ receive a copy of a value's fields, never a pointer into a block, which moves when the list grows.
  • L9: if a read-only list comes, a list<Point> passes for a read-only list<any>, reads giving values by section 6.
  • The name: there is one type, the list, and it is printed as list<int>, list<Point>; bytes is printed as bytes.

14. A worked case: the bounce example on every core

examples/bounce_parallel.astra moves 50,000 balls a frame on every core and draws them on one. Today each ball is an object that move changes in place:

class Ball(var x : number, var y : number, var dx : number, var dy : number, val radius : number, val color) {
  fun move(width : number, height : number, steps : number) {
    x += dx * steps
    y += dy * steps
    if x < radius { x = radius; dx = dx.absoluteValue }
    if x > width - radius { x = Math.max(radius, width - radius); dx = -dx.absoluteValue }
    if y < radius { y = radius; dy = dy.absoluteValue }
    if y > height - radius { y = Math.max(radius, height - radius); dy = -dy.absoluteValue }
  }
}

val balls = []
balls.parallelStream().forEach { it.move(width, height, steps) }      // the one line
for ball in balls {
  canvas.color = ball.color
  canvas.fillOval(ball.x - ball.radius, ball.y - ball.radius, 2 * ball.radius, 2 * ball.radius)
}

With a mutating method

The ball becomes a value type with var position and speed, move is marked mutating, and the list is a list of balls. Everything else, the one parallel line included, is as it was:

value Ball(var x : float, var y : float, var dx : float, var dy : float, val radius : float, val color : Color) {
  mutating fun move(width : float, height : float, steps : float) {
    x += dx * steps
    y += dy * steps
    if x < radius { x = radius; dx = dx.absoluteValue }
    if x > width - radius { x = Math.max(radius, width - radius); dx = -dx.absoluteValue }
    if y < radius { y = radius; dy = dy.absoluteValue }
    if y > height - radius { y = Math.max(radius, height - radius); dy = -dy.absoluteValue }
  }
}

val balls = list<Ball>()
balls.parallelStream().forEach { it.move(width, height, steps) }      // each core moves its own share, in place
for ball in balls {                                                    // read in place
  canvas.color = ball.color
  canvas.fillOval(ball.x - ball.radius, ball.y - ball.radius, 2 * ball.radius, 2 * ball.radius)
}
  • What changed: class to value; number to float and a type for color (M6.5's types); mutating in front of move; and [] to list<Ball>(), which M6.5 asks for anyway, since an empty list has no item type to infer. balls.add(Ball(...)) in addBall is unchanged and writes the new ball straight into the list (section 7).
  • How it runs: each core is dealt a range of positions (section 11); it is the item itself, since the list hands it over and the lambda keeps nothing; move writes straight into the item. Nothing is copied or allocated.
  • What the compiler checks: that move assigns only var fields (radius and color are val), and that it is a place where move is called on it.

Without one: a method that returns the moved ball

value Ball(val x : float, val y : float, val dx : float, val dy : float, val radius : float, val color : Color) {
  fun moved(width : float, height : float, steps : float) : Ball {
    var nx = x + dx * steps
    var ndx = dx
    if nx < radius { nx = radius; ndx = dx.absoluteValue }
    // ... the other edge, and the same for y ...
    return Ball(nx, ny, ndx, ndy, radius, color)
  }
}

balls.parallelStream().replaceAll { it.moved(width, height, steps) }   // each core its own share

No allocation either: it is read in place, and moved builds its result straight into the item (section 7), after reading all of the old ball.

What it saves

  • Memory: today a ball is about 300 bytes (the object, a field table grown to 8 entries, and its place in the list), about 15 MB for 50,000; as a value in a list, 48 bytes (five floats and a reference to its Color), 2.4 MB. (From the layouts, not measured.)
  • Speed: move today finds x, y, dx and dy by name in each ball's field table, about ten look-ups per ball per frame; as a value, each is at a fixed offset. Drawing walks one block of memory.

15. What it costs

Memory, for a million Points: about 190 MB as objects today; 16 MB as a list of values (32 MB at most while it grows).

Speed (estimates, to be measured):

  • Reading a field of an item: an address calculation and a load, cheaper than today's look-up by name. Walking a list of values: memory read straight through.
  • Reading a field of any value: one test for which of its four forms it is.
  • Replacing an item: copying its bytes, where today a new object is made.
  • Keeping an item of more than 8 bytes: one box (about 32 bytes for a Point), where a list of objects hands out the object it has. A program that keeps many items of a large value type does better with a class.
  • Large items reordered: sorting moves each item once (section 9); inserting and removing in the middle copy the items after the position, more bytes than references would be.
  • Generic list code: the check of section 10, 1 to 3%, until copies per layout remove it.
  • Switching threads: one scan of the outgoing stack. Collection: a list is one object to trace instead of a million.
  • Lists of objects: nothing changes for them.

Build cost: large, though in steps that each stand alone: value types and boxes, three storage kinds for lists, references into lists and objects, the compiler's analyses (parameters that keep, functions that change lists or assign fields), results built where they go, assignment through places and mutating methods, small values in place, values inside objects, the scan at thread switches, the sort through positions, and copies of generic functions per layout.

16. Building it, in steps

Each step works and is measured on its own. All of it is M6.6.

  1. Value types as boxes. value, fixed layout, equality, printing, copy. Needs M6.5's types and the fixed field layouts of its part 4. Measured: Jade's layout with Dimension, Rectangle, Point and Insets as values.
  2. Lists of values, copying on every read that leaves its expression. The storage kinds, the operations, the sort through positions, references into lists within an expression, the thread-switch scan, the check in generic code, and constructor calls and copy stored straight into items (section 7, rule b). Measured: a million points built, summed, sorted, walked.
  3. The compiler's analyses. Parameters that do not keep, functions that change lists, locals that go nowhere. Checked with the copy-every-read stress setting. Measured: a million particles updated and drawn for a hundred frames, with no copy made.
  4. Results built where they go (section 7, rule a): the hidden destination, the scratch space, the new forms of call and return. Measured: the bounce example on every core, returning moved balls, with no allocation in a frame.
  5. Changing through a place (section 8): field assignment through places, mutating methods, it as a place. Measured: the bounce example with its move unchanged.
  6. Small values in place (section 4). Measured: a Color-heavy drawing loop, with no box made.
  7. Values inside their objects (section 4), with the analysis of which functions assign which fields. Measured: Jade's layout, with bounds and the cached Sizes inside their components.
  8. Copies of generic functions per layout (section 10), for the standard library's list functions first. Measured: map, filter, sumOf and sort on a list of points, with and without.

17. A possible later upgrade: references that follow an item

An earlier version of this design made val p = pts[42] a reference that stays with its item through sorts, inserts and removals, without a copy: each item in a storage slot that never moves while referenced, an index from positions to slots, a bit per slot marking those that may be referenced, and the collector clearing the bits and freeing slots left behind. It would take away two of the costs of section 15, the box when an item is kept and the moving of large items when inserting, sorting or removing (only 4-byte positions would move), at the price of an extra step on reads once indexed and work for the collector. Worth building only if measurements show those two costs matter; with values a copy reads exactly the same, so it would change speed, not meaning.

18. Questions for you

  • Value types holding strings and objects: decided: yes.
  • The word for a value type: decided: value Point(...).
  • bytes: decided: list<byte> (which the earlier pack<byte> now is).
  • Size: decided 2026-10-18: any size, up to the 64 KB that a reference's offset allows; the type's author chooses class for large things that are kept and reordered.
  • Nullable value types (list<Point?>, list<int?>): decided 2026-10-18: packed as the items of a list of values are, with a bit per item for null, kept beside the items (the bits move with them when items are inserted, removed and sorted). Measured on two uses with 16-byte items, against 16-byte values with a box per item and against a null flag inside each item: a weather station's million readings, 5% missing, and a spreadsheet's 100,000 rows of ten cells, 30% empty. Packed with bits was the fastest or close at everything: changing every reading 1.7 ms against 30.5 boxed and 3.8 with flags, building 20 against 44 and 26, sorting 60 against 104 and 63, no collection against 19 ms boxed, in 16 MB against 48 and 24; inserting and removing in the middle cost about the same as boxed and about half as much as flags, which move 24 bytes an item. A list of a nullable value type is therefore as compact and fast as one of the value type.
  • The sort through positions: decided 2026-10-18: from 32 bytes an item to begin with, tuned by measurement.
  • replaceAll { }, Kotlin's name for replacing every item with what a lambda gives for it: decided 2026-10-18: kept.
