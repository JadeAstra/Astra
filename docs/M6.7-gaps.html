M6.7: gaps to close

Gaps to be dealt with in M6.7, the faster VM, with what has been decided about them so far (G4's design). Gap numbers are kept from where the gap was found: these were found in M6.6 (M6.6-gaps.html) and placed in M6.7 there. The plan is in gui-plan.md.

Gaps

No.PartGapWhen
G42A generic value type keeps no type arguments when the program runs: a Two<int, string> is any Two to is and as, and Two<int, string>(1, "s") as Two<string, string> passes. Decided with the user (2026-10-22), to be built with M6.7:
  • The type arguments are kept where the class is already kept, at no cost in bytes: a small value's entry in the table of small classes becomes one for the class with its type arguments (Id<User>), a box's header names the same, and a value kept inline takes them from the list's or the field's declared type (or the object's own type arguments, for a field declared Id<T>).
  • A value stored in a container declared wider (a Pair<int, int> in a List<Pair<Number, Number>>) takes the container's type arguments: no boxing, and no list left unpacked because of it.
  • A phantom type parameter, one the contents cannot show (in no field, only in a function type, or only inside a collection that keeps no type), keeps its own: in a container declared wider than it (List<Id<any>>, a field Id<any>) each item or field has a hidden slot of 8 bytes holding its argument, the layout chosen from the container's declared type when it is made; elsewhere it costs nothing, the declared type saying it already (option B).
  • == and hashCode ignore type arguments, as Kotlin's do: Id<User>(7) == Id<Order>(7), and they are one key.
  • is and as go by the recorded type arguments, refined by the contents where a recorded one is wider: a recorded argument that fits the one asked passes; a wider one passes if every field declared with that parameter fits it (Pair(x, y) with x : any, recorded Pair<any, any>, is a Pair<int, int> when both are ints); one that does not overlap fails. A cast gives a copy recorded with the narrower arguments; a value is copied and never shared, so the view cannot be undone behind it. null fits a nullable argument only. Reflection (p#) shows the recorded type.
  • Making a value in generic code finds its class-with-arguments entry through a cache at each place, as G3's; a value sent to a worker has its type found again there, each worker having its own table of types.

G65AllCode placement alone moves the fields benchmark by 10 to 20% with the same loop, under MSVC and under Clang. Not a gap in Astra, but a caution in reading timings: compare against a baseline built the same way, and count instructions, before calling a change slower.
  • Seen again 2026-10-24 (G16), on the Clang build the benchmarks use, with fields' bytecode identical before and after: +11% with an atomic counter added to FinishClass in run(), +2.6% with it moved to a function of its own, +6% when a rarely taken read past ?. in GetProp was moved out of run() as well. Again with D162 (a new function and three property reads changed in vm.cpp, none of which these run): bounce_classes +7% and fields +8% against the commit before, both with their bytecode identical; and numeric +7% with G22. The VM's loop is one large switch built with Release's flags alone (no profile, no link-time optimisation, no alignment), so an edit anywhere in vm.cpp can shift where the hot cases fall against cache lines and the branch predictor's tables.
  • What could be done, most useful first, to be tried when the loop is rewritten for D160:
    1. Profile-guided optimisation with Clang: a build that counts, the benchmarks run on it for a profile, and the build made from that profile, laying the hot paths out by how often they run rather than by where they are in the source. Interpreters usually gain 10 to 20% from it as well. Costs an extra build step with a training run, and a profile to make again as the VM changes.
    2. Alignment, such as -mllvm -align-all-nofallthru-blocks=5: every jump target starting on a 32-byte boundary, so that a change elsewhere does not move the hot cases. Cheap to try; it may help or slightly hurt, which only a measurement tells.
    3. A comparison that allows for placement: each side built in a few shuffled layouts (lld-link's function order) and the spreads compared, not one number. Nothing faster, but a real slowdown told from placement.
    4. Rare paths kept out of run(), as now (VM::typeInstruction, VM::placeInstruction, VM::classFinished). It helps, one change at a time.
    To be measured for speed and for steadiness: a cold function of no use added to vm.cpp, and how far fields moves with it.
