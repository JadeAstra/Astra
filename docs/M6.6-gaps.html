M6.6 so far: what is left open

The choices made while building M6.6 that are not yet confirmed, and the gaps it left, each with where it is to be dealt with: the first half, parts 1 to 7, and of the second half, part 8's groups as they are built. Written 2026-10-19, and brought up to date after each part since: the gaps they closed are gone from the list. The same items are in gui-plan.md (the M6.6 notes, D162 to D180 and the Open list); the design is in value-lists.html.

Contents

  • Choices to confirm (nineteen from the first half; seven from part 8, group 1; twelve from group 2; eleven from group 3; eleven from group 4; eleven from group 5; eleven from group 6; thirteen from group 7; eleven from group 8; twelve from group 9)
  • Gaps left (forty-six; those for M6.7 are in M6.7-gaps.html)

Choices to confirm

D162The type of items.itemType (part 1)

A new built-in type, Type: a type as the program runs. items.itemType, map.keyType and map.valueType give one (any for a collection made without its type). It prints as written (List<int>), two are == when they are the same type, and x is Type tests for one.

Your choice

D163How the C++ functions' results are checked (part 1)

By a test setting, not on every call. ASTRA_CHECK_NATIVE_RESULTS=1 compiles a check after every call of an external function against its declaration; the suite passes with it, and each checkpoint would run it beside the GC and thread stress settings. The C++ is fixed code, so the suite proves its declarations once, and later parts can then trust them while the program runs. The other way, a check on every call, costs every call of the C++.

Your choice

D164What the check changed in the standard library (part 1)

  • The coerce functions give one of their numbers as it was, so float.coerceIn(Number, Number) and the like now say Number, with forms for all ints and all floats that say int and float. (2.5.coerceIn(0, 1) is the int 1.)
  • A type parameter that the object a call is made on says nothing of (a Map written without type arguments) is unknown, not taken from the arguments: data.get(key, "missing") is no longer typed string? there.
  • Deque.toList builds a List<T> rather than casting its List<T?>, and Set == gives false for a set of other things rather than failing at a cast, now that casts are checked in full.
Your choice

D165The rules of a value type, as built (part 2)

  • value Point(val x : int, val y : int) needs a header whose entries are all fields. It is a data class: printing, ==, copy, coming apart.
  • It may implement interfaces, extends no class, and no class extends it.
  • A field is given its value in the header, where it is declared in the body (one declared there with none is an error), or in the type's init; never again. p.x = 4, and x += 1 in a method, are compile errors saying to make a changed copy, until changing through a place (part 4).
  • === on a value type is a compile error, as a value has no identity; through any it compares contents.
  • A value type cannot hold itself except where that field may be null; the checker reports it.
  • Every core may read a value, since it never changes.
Your choice

D179Jade's geometry as value types: decided (part 7)

You chose on 2026-10-19 to make Jade's Point, Dimension, Insets and Rectangle value types, and Jade's Sizes with them: a component's bounds and the sizes it keeps are inside it, and setSize, translate, setLocation, grow and setBounds are mutating methods. Nothing in Jade relied on sharing one; one val that was translated became a var.

D180Rectangle takes all four numbers (part 7)

A value type is made from its header alone, and Astra has no constructors of other forms, so Rectangle(x, y, width, height) takes all four with no defaults. Java's Rectangle() is Rectangle(0, 0, 0, 0) and Rectangle(w, h) is Rectangle(0, 0, w, h): both are compile errors as written, so that Rectangle(30, 40) cannot quietly mean the corner. Rectangle(other) is other, which is copied wherever it is kept. Point(), Dimension() and Insets() keep their zeros, as in Java.

Your choice

D166Lists of values, as built (part 3)

  • A list is packed when it is given its type (by its literal, by what it is declared as, or at the call of a C++ function that made it): List<int>, List<float>, List<bool>, a value type's list, and the nullable ones of those.
  • Putting in a value the list was not made to hold is an error where it is put in (cannot put a value of type string in a List<int>), which an unchecked cast through List<any> used to allow.
  • A copy of a list (toList, slice, subList, reversed, + of two of one type) keeps its type and how it is kept.
  • sortBy and sortByDescending, for every list, call the selector once per item rather than twice per comparison (a million items sorted in 70 to 130 ms instead of 1.5 s). A selector with side effects sees fewer calls.
Your choice

D167Changing a value through its place (part 4)

  • A var field of a value is changed only through a place that holds the value: a var variable (local, global, or one a lambda holds), a var field of an object, an item of a list, a value's field that is itself a place, or a lambda's parameter (what forEach { it.move() } is given). So p.x = 4, p.x += 1, pts[i].y++, line.to.x = 9.
  • A mutating fun may change this's fields and call the type's other mutating methods, and is called only on a place. mutating on anything but a value type is an error.
  • A variable or field changed this way gets a value of its own first, so val q = p; p.x = 10 leaves q as it was.
  • Every part of pts[next()].x += 1 is worked out once.
Your choice

D168Reading a value where it is (part 4)

  • A value read from a list or another value (pts[i], a loop's item, a lambda's it, a parameter, this) is not copied where the checker shows that nothing which may change a list of its type runs while it is in use, through what the code calls, overrides included. Changing a list means removing, inserting, sorting, setting or replacing items; adding at the end is not, as a reference into a list is by position. A function given as an argument counts as one that may.
  • A loop is judged by its body. If the body gives the item to a variable from outside the loop, the loop is judged by the whole function, as the item might be used after it.
  • A call that may wait counts as one that changes every list, since other code runs meanwhile: a flow that waits in a loop reads each item as it was when the loop came to it.
  • Whatever keeps a value longer than the stack does (a field, a list, a global, a variable a lambda holds, a C++ function) takes a copy.
  • The test setting ASTRA_COPY_READS=1 copies every read; the suite prints the same with it.
Your choice

D169Results built where they go (part 4)

  • pts[i] = f(...), where f gives a value of the list's type, gives f the item as where its result goes. A function that gives a value passes that on to a call whose result it returns, and making a value from its header alone writes its fields there, every argument worked out before any is written.
  • So pts[i] = pts[i].moved(1), pts[i] = Point(...) and pts[i] = pts[i].copy(x = 4) make no copy.
  • list.replaceAll { it.moved() } replaces each item by what the lambda gives, built where the item is.
Your choice

D170Parallel sections over a list of values (part 4)

  • pts.parallelStream() deals each core its own part of the list and hands it the items where they are: forEach { it.move() } changes them there, map and the rest read them there.
  • parallelStream().replaceAll { it.moved() } replaces each item, on every core, built where it is. On a list of anything else it puts what the lambda gave in once every core is done.
  • A core reads and writes only its own part (pts[0] from another core's part is an error saying so), and changes the list itself not at all (sortBy, sortByDescending and replaceAll now count as changing a list, as they should have already). A built-in function given the whole list is refused, but for isEmpty and isNotEmpty.
Your choice

ThreadsNo scan at a thread switch (part 4)

The plan was to replace a thread's references into lists by copies whenever it gives up the lock. Not built, and proposed not to be: a thread gives the lock up only at a call or the end of a loop body, and another thread reordering a list meanwhile is a race, which Astra lets give a wrong answer but never damage anything. A reference into a list is checked against the list's length and its type of item every time it is used, so a race at worst reads or changes another item, as it would with objects. A flow is not a race (other code runs at the points where it waits, by design), and the checker handles it (D168).

Your choice

D171Small values in the value itself (part 5)

  • A value type whose layout is at most 8 bytes and holds no object (value Rgba(val argb : int), value Meters(val m : float), value Flags(var on : bool, var shown : bool)) is kept in the value itself: its fields in the 8 bytes a value has for its contents, its type's number beside them.
  • So in variables, arguments, results, fields, lists and maps it takes no box and allocates nothing. The program sees no difference.
  • C++ functions are given one in a box, as they are given every value of a value type; list.add excepted (D174).
  • Measured: bench/colors_values.astra, 100 frames of a 320 by 240 picture blended from a palette, 24 to 31% faster than in part 4, with no box made where part 4 made 15.4 million.
Your choice

D172Values inside their objects (part 5)

  • A field of a value type larger than 8 bytes, not null, is kept inside its object, after its other slots, laid out when the first object of the class is made.
  • comp.bounds = r copies the value's bytes in; comp.bounds.w = 30 and comp.bounds.origin.move(1) change it there; comp.bounds = Rect(...) and cached = measure() build it there.
  • A field is laid out so when its type is written, or when it is given a value made by its type's name (var cached = Size(0, 0)). A field of an object made before its class's field types exist keeps a box.
Your choice

D173Fields and results read where they are (part 5)

  • Giving a field of a value type another value counts, for D168, as a change to values of that type, as changing a list of them does.
  • A field kept inside its object is read where it is (a reference into the object) where nothing that may change values of its type runs while the read is in use; otherwise it is copied.
  • What a function gives back that it read where it is stays so where the caller is shown to be as safe; a call's result read at once by one of its fields (node.sizes().pref), and a field given back by return, always are. Elsewhere a function gives back a copy.
  • Measured: bench/layout_cached_values.astra, Jade's layout with each component's Sizes kept inside it, makes 1,215 boxes where part 4 made 57,126; its time is 4 to 7% more, from the reads through references (G14).
Your choice

D174list.add copies where the item is (part 5)

out.add(p) for an item read where it is, in a loop say, copies its bytes straight into out, with no box made for it on the way: filtering a million points by hand takes 43 ms instead of 65. add(i, item) copies the item first, since the items after i move.

Your choice

D175Generic functions copied per layout: not now (part 5)

Measured on a million points: map 46 ms against 41 written out by hand, sumOf 25 against 23, filter 98 against 43, sortedBy 84. The check that generic code makes costs a few percent. filter's difference comes from copying each item it hands to its lambda, since the lambda might change the list; inline functions (D59, the second half) remove that, and copies per layout would not. Proposed: copies per layout wait until a measurement asks for them.

Your choice

D176A number's conversions and Math's functions as instructions (part 6)

x.toInt(), toLong(), toFloat(), toDouble(), roundToInt(), roundToLong(), isNaN(), isInfinite(), isFinite(), and Math.sqrt, floor, ceil, round, abs, and min and max of two ints or two floats, where the checker knows the call is the standard library's, are one instruction each, giving what the library's own gives, errors included. Drawing a million particles a frame is 34 to 40% faster.

Your choice

D177Fields kept as their payload alone (part 6)

  • An int, a float or a bool field whose type is known (written, or worked out from what it is first given), and not null, is kept in its object as its 8 bytes of contents alone, before the object's slots, at the same place in every object of its class. An object of three float fields takes 72 bytes in place of 96: a million of them, 112 MB at most against 142.
  • A val, and a field an init must set, has a bit saying whether it has been given a value, so that giving a val a second value, and an init that leaves one unset, are still errors.
  • Any other payload reads as 0, 0.0 or false before it is first given a value, where a slot read as an error. (Only code that reads a field before the line that gives it its value sees the difference.)
  • Field reads and writes are as fast as before, with Clang and with MSVC.
Your choice

D149Values in variables, in M6.7 (D178)

Values of up to 32 bytes kept in consecutive slots of a frame (D149) need the same change to how a frame's slots are laid out as frame slots that keep only a payload. You decided on 2026-10-19 (D178) that those, with instructions chosen by type for arithmetic, come with M6.7's rewritten loop. Until then a value larger than 8 bytes in a variable, an argument or a result is a box.

SizeThe largest value type (from value-lists.html)

Decided "any size, up to 64 KB". Offered on 2026-10-18 and not yet answered: "any size, with a copy on read past 64 KB". The limit comes only from the 16-bit offset in a reference into a list item, and only fields kept in place count towards it.

Your choice

8.1aA byte becomes an int by toInt() (part 8, group 1)

D19 says byte arithmetic gives an int and an int becomes a byte by toByte(); it does not say whether a byte goes where an int is asked for. As built, it does not: b.toInt(), as an int goes where a float is asked for only by toFloat(), and as in Kotlin. Comparing (b < 255, b == 200) and arithmetic (b + 1, an int) take a byte and an int together. An int literal that fits, or arithmetic on literals, is a byte where a byte goes; a name, even a constant's, is the int it is, as in Kotlin (val n = 5; val b : byte = n is an error).

Your choice

8.1bWhere a char goes for a string (part 8, group 1)

A char goes where a string is asked for only where Kotlin has a form taking a Char: split(','), indexOf('x'), lastIndexOf, contains, startsWith, endsWith, replace('a', 'b'), padStart(n, '0'), padEnd. Elsewhere it is an error saying a string is wanted ("$c" or c.toString() makes one). So a Map<string, V> indexed by a char is a compile error, though when running 'c' and "c" are one key, as a Map<any, V> shows (D25). The other way would be a char taken wherever a string is, made one as it is passed.

Your choice

8.1cA char's upper() and lower() give a char (part 8, group 1)

D74 keeps upper and lower over uppercase and lowercase; on a char each gives a char, the letter in the other case where that is one character, the char itself otherwise. Kotlin's Char.uppercase() gives a string (for ß, "SS") and its uppercaseChar() a char; ported replaceFirstChar { it.uppercase() } becomes { it.upper() }. A string keeps uppercase() and lowercase() beside upper() and lower() until D74 is built.

Your choice

8.1dThe UTF-8 a string is made from is not kept (part 8, group 1)

D20: a string's UTF-8 form is made when first asked for and kept. As Python does, a string made from UTF-8 (read from a file, joined by C++ code) keeps only its characters, at 1, 2 or 4 bytes each, and makes its UTF-8 again when C++ code first asks for it: Latin-1 text then takes a byte a character, not UTF-8's two for é. ASCII text is its own UTF-8, so the question is only for other text. Keeping the UTF-8 it came from would save that pass and cost the memory of both forms.

Your choice

8.1eThe byte order of Bytes' numbers (part 8, group 1)

L0 gives int16(at), int32(at), float32(at), uint16(at), uint32(at) and their put forms "with a byte order". Built as a flag, bigEndian = false by default: buffer.uint32(4, bigEndian = true), buffer.putInt16(0, -2). The other way would be an enum, ByteOrder.big.

Your choice

8.1fwrap32() beside toInt32Wrapped() (part 8, group 1)

D148 names both, and they give the same: the low 32 bits as a signed number. Both are built; one name for each thing (D74) would keep one, wrap32() for the hashing it is meant for, or toInt32Wrapped() for its family.

Your choice

8.1gWhat hash(a, b, ...) combines (part 8, group 1)

Java's Objects.hash rule, 31 * h + hash of each, wrapping at 32 bits, over Astra's own hash of each value (the one map keys use: by contents for strings, frozen collections, data classes and values), and a class's own hashCode for an object of one (since group 2, 8.2d).

Your choice

8.2aThe names FrozenList and open List (part 8, group 2)

D26 and D32 write frozenList, frozenMap, frozenSet and open list. Built after the naming rule, which writes every type but the fixed lowercase set in title case: FrozenList<T>, FrozenMap<K, V>, FrozenSet<T>, open List<T>, open List<accepts Button>. Kotlin's MutableList<T> is an error naming open List<T>.

Your choice

8.2bBytes are no key (part 8, group 2)

Bytes can change, so by D26 they cannot be a key, and D26 names no frozen form of them. As built, a key of bytes is refused with the advice key.toList().frozen(), a FrozenList<byte>. The other way would be a frozen Bytes, bytes.frozen(), kept as bytes.

Your choice

8.2cWhat the checker follows to tell a key that can change (part 8, group 2)

A class with its own == or hashCode can be a key when they read nothing that can change. The checker follows them into the methods and getters they call that have bodies, on the object or on others; a var field read anywhere there makes the class no key, as does a val field of a type that can change, or a call it cannot follow (a function of the C++, an abstract one). A value type may read its var fields, since a value goes into a map as a copy. Getters were followed after Jade's Color, whose == reads its rgb getter, would otherwise have been no key. For Map<any, V> the class carries the answer, marked when compiled (Op::UnstableKey), checked at each new key.

Your choice

8.2dhashCode() for every value, and what hash calls (part 8, group 2)

Every value has hashCode(): a class's own where it has one, otherwise the hash a map takes for it (by contents for strings, numbers, chars, frozen collections, data classes and values; by which object it is for any other), folded to 32 bits. hash(a, b, ...) now calls a class's own hashCode for an object of one, which settles 8.1g's question. An int's hashCode() is the map's hash of it, not the int itself as in Kotlin.

Your choice

8.2eHow deep frozen() goes (part 8, group 2)

frozen() copies a list, map or set, and the lists, maps and sets inside it, all frozen; objects, values and Bytes inside are kept as they are. A frozen collection holding something that can change (a data object with a var, bytes) is frozen, but no key: the checker says so where the type shows it, and the program when it runs. frozen() of a frozen collection gives it back.

Your choice

8.2fWhich results are open (D45) (part 8, group 2)

Open: what every standard-library function that makes a new list, map or set gives (filter, map, sorted, toList, listOf, mapOf, setOf, split and the rest), a slice, + of two lists, and a vararg parameter inside its function; groupBy gives an open Map<K, open List<T>>. Read-only: emptyList(), emptySet(), emptyMap() (as Kotlin's), what gives its receiver back (orEmpty(), ifEmpty, onEach), a map's keys, entries and values, and what an object hands out of its own (ProcessBuilder.command()).

Your choice

8.2gopen is the checker's alone (part 8, group 2)

When the program runs a list is a list: x is open List<int> and x as open List<int> on a value of type any test only List<int>, so a frozen list passes and fails when changed. Frozen collections are known when running: is FrozenList asks the list. Keeping a read-only mark on each list passed through a read-only name is the other way, at a cost on every pass.

Your choice

8.2hmutableListOf and the like are kept (part 8, group 2)

listOf, setOf and mapOf give open collections already, so Kotlin's mutableListOf, mutableSetOf, mutableMapOf, arrayListOf, hashMapOf and the rest make the same thing. They are kept for ported code; one name for each thing (D74) would make them errors naming listOf. Likewise insert(i, x) beside Kotlin's add(i, x).

Your choice

8.2iA set or a map's view changed while a for goes through it (part 8, group 2)

The loop sees it as it is: an item added while it runs is reached, one removed is not, and nothing is an error. Kotlin throws ConcurrentModificationException; a list in Astra already behaves as a set now does.

Your choice

8.2jMessages name open (part 8, group 2)

A type in a message is written as it is: "an open List<string> has no method 'nope'", "first(...) takes a List<string> for 'items', not an open List<int>". The other way would leave open out wherever it does not decide the error.

Your choice

8.2kWhat is read through accepts (part 8, group 2)

D34: through open List<accepts Button> reading gives any. Built as any?, since the list may be one of a nullable type above Button. accepts anywhere but an open list's, set's or map's items is an error.

Your choice

8.2lPositions: ^k a value, a negative one an error (part 8, group 2)

^k is a value of type Index: it can be kept (val last = ^1) and passed, and an int is one counted from the start. A range with a ^ end (2..^1) is only for slicing, and a for over one is an error. A negative position written as a literal (items[-1]) is a compile error naming items[^1]; a computed one is out of range when running. A slice past the ends is an error, as an index is; take and drop clamp.

Your choice

8.3aWhat may be lateinit (part 8, group 3)

As in Kotlin, a field that holds an object: not an int, float, bool, char, byte or storage width, which always has a value, nor a value type, kept whole where it is. Only a var of a class, its type written and not null; not a static, a top-level variable or a local. Reading it before it has a value is an error naming it. Kotlin's ::x.isInitialized waits for reflection (group 6).

Your choice

8.3bHow lazy is kept (part 8, group 3)

A lazy field, static or top-level value holds the "no value yet" mark every read already tests for, with what works its value out beside it; the first read puts the value in its place, so a read after that costs what any field read does: D37's "one test per read" at no added cost. Not for a local, nor in a value type. A thread that reads it while another is working it out waits by handing the lock over until the value is there. A lazy starting value may not wait, as nothing that starts a value does.

Your choice

8.3cWhich objects are made when first used (part 8, group 3)

D66: a named object at the top level of a file, or inside a class, is made when first used, under lazy val's rules. One declared inside a function is made where it is written, as a local is not kept lazily. No program in the suite relied on the old order.

Your choice

8.3dWhere a kind is written by its bare name (part 8, group 3)

D39: a kind of an enum class by its bare name wherever one is expected: a value given where the enum class is declared (a variable, an argument, a result, a list item), a when's branches over one (Close ->), and after is where the value is one (is Click). The kinds of a kind that is itself an enum class are found too. A name that already means something keeps that meaning. The checker settles it; nothing is left to the running program, unlike an enum's entries.

Your choice

8.3eWhen inference gives a union (part 8, group 3)

D40: two types with a class or interface above both give that, as before; with none, the union (flag ? 1 : "one", [1, "one"]), where they used to give an unknown type. Eight tests and one line of Jade had to say any or test the type. A union's members are those of the nearest type above all its types. A local is narrowed the other way too: after if (v is string) return, v is the rest. is and as on a whole union are errors, nothing of it being kept when running.

Your choice

8.3fA name for a type that refers to itself (part 8, group 3)

D41 allows it inside another type (type Json = ... | List<Json>). Built so that inside it, it is any: a List<Json> is checked as a list of anything, the outer level as the union it is.

Your choice

8.3gKotlin's accessors and what they take (part 8, group 3)

D68: the setter takes the property's type unless it says another (set(text : any?), which Jade's Native.clipboardText keeps so that a number may be set); Kotlin allows no other type. A property that could only be set, and a subclass replacing only half of a property, have no Kotlin form: the tests that had them now write the whole property, reaching the one above with super.name, and super.name = value was added for that. A static property is written the same way, in the static block, and keeps nothing of its own.

Your choice

8.3hWhat goes in the one static block (part 8, group 3)

D67: every static member, const included, and static properties in Kotlin's form. The 163 prefixed statics of the standard library, Jade, the examples and the tests moved into their classes' blocks, keeping their order and comments. companion object is an error naming static { }.

Your choice

8.3iHow a data class passes its parent's fields up (part 8, group 3)

D65 says the child's header starts with the parent's fields. As built, of the same types, and they are passed up as they are, : Point(x, y), written out; the alternative is to pass them without writing it.

Your choice

8.3jWhat extend covers (part 8, group 3)

D33 for classes and interfaces, of the program or a library. A built-in type (extend string : Comparable) is not yet: its values have no class to carry the interface. Two extends of one class and interface are taken as the same when they bridge the same names. The checker holds an extend where it is in reach; when the program runs, an extend holds once its file is loaded, so is on a value of type any answers by every extend loaded.

Your choice

8.3kWhich extension function a call finds (part 8, group 3)

D70: those in reach, the file's own folder's first, then what it imports, and the standard library's. When running, an extension function is still found by its type and name, so two libraries giving one type an extension of the same name with the same parameters would meet; with one library (Jade) this cannot happen yet.

Your choice

8.4aWhere an infix call may break (part 8, group 4)

D72: the name is on the line its left side ends on, as Kotlin asks, and what it is given starts on that line too; Kotlin lets that go on the next line. A word at the start of a line begins something new, so a statement can never be joined to the one above by accident. and and or stay Astra's logical words and cannot be infix names.

Your choice

8.4bWhat a lambda given as an interface is (part 8, group 4)

D28: one small object of a class made once for each place it is written, whose method calls the lambda, so is Action holds and the interface's default methods come with it. Kotlin's Action { ... } makes one too; fun (x) { } converts as a lambda does. Between overloads taking a function type and an interface, the function type is chosen, which needs nothing made; between two interfaces, an error asks which.

Your choice

8.4cWhich calls of itself are a loop (part 8, group 4)

D29: return f(...), an expression body, and a branch of ? : or what follows ?: in what is returned, with arguments by position, for a top-level function, an extension, and a method called on its own object (bare or this.) that nothing overrides. Not one on another object of the class, not in a when or if giving the value, not inside a try, not for a generic function or one declared inside another (gaps). A left-out argument is worked out again from its default. The trace says 10,001 times, counting every call it stood for.

Your choice

8.4dWhat tail asks (part 8, group 4)

D29: each call of itself made directly in its body is its last step; one that is not is an error saying why (its result used afterwards, a try around it, the function generic, a subclass overriding it). A call from inside a lambda in it is not looked at. Kotlin's tailrec is an error pointing to tail.

Your choice

8.4eWhen a nested it is an error (part 8, group 4)

D55: when the inner lambda's own it is used inside a lambda that uses its own; the error is at each inner use. A lambda given a type that takes nothing has no it, so one inside it is the outer lambda's, which is not an error. Before, such a lambda had an it that was always null.

Your choice

8.4fWhat this@Name names, and this in a block (part 8, group 4)

D57: the class's simple name for the object of a method of it, the function's name for an extension's receiver, and for a block run on an object its label or the name of the function it is given to; the innermost first. Jade lays text out in units rounded up from the screen's pixels (D2), in a class of its own, TextUnits, internal to Jade.

Your choice

8.9hThe style handed to a component (part 8, group 9)

D132 moves the style from the canvas to the component. As built, paintInto(canvas, given = null) takes the style handed down as an argument, works out styleIn(given ?: style()) and keeps it as paintStyle; a container hands each child nothing, so the child paints in its own style, as it did when the container made the child's canvas with the child's style. Content now has var owner itself, so OwnedContent is gone and every content declares the field.

Your choice

8.9iPictures of a component, and where the card copy is kept (part 8, group 9)

As built, renderFrame and renderToImage draw on a Surface, on the graphics card as a window is, and give its pixels back as an Image, so a test sees what a window shows. D124 keeps an image's copy on the card in a slot of the C++ only the native layer uses; as built the slot is fields of Image internal to the standard library (the copy, the change number it was made at and the rectangle changed since), which no program can see, and the copy goes when the image is collected. inkBox gives a Rect or null.

Your choice

8.9jHow finely curves are drawn in memory (part 8, group 9)

An image's canvas fills shapes with the text engine's rasterizer, which cut curves into pieces for small glyphs, to within about a sixth of a pixel: an oval came out 1.6% short of its area. As built, shapes are cut about ten times as finely, so an oval's pixels add up to its area to within a pixel; glyphs are cut as before, so text draws exactly as it did. The graphics card draws ovals by distance in a shader, as before.

Your choice

8.9kOld static names of the standard library (part 8, group 9)

D144 makes Font.bold, Font.plain and Font.italic errors showing the named form. The checker did not report a static member a class lacks at all (one turned up when the program ran), because it does not keep a class's static properties with getters or a superclass's statics reached through a subclass. As built, a static name a standard-library class lacks is an error only where there is advice for it; other missing static names are found when the program runs, as before (G57).

Your choice

8.9lAn image with no see-through pixels (part 8, group 9)

L57 asks that each change to Jade's API be asked first. JadeUI's BufferedImage had a type with no alpha (TYPE_INT_RGB), whose pixels are always solid; an Image always has alpha. A flag such as Image(w, h, opaque = true), under which a pixel set see-through is made solid, was not built: it is yours to decide. Until then a ported TYPE_INT_RGB image is an Image filled with a solid colour.
