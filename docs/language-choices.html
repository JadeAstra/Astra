The decision is yours.

  • Summary

Kotlin made a number of choices because it runs on the JVM, works with Java code, or has to keep older Kotlin code working. Astra has its own VM, no Java to talk to and no older compiled code to keep running, so each of those choices can be made again on its merits.

This document lists them as decisions for the user, written 2026-10-14 during M6.5 (static types, plan section 5.7). Each entry gives the question, what Kotlin does and why, what other languages do and why, the options with what each gains and loses (run speed included), and a recommendation. The box at the end of each entry is for the user's decision.

Each entry also says what Kotlin intends where the technology allows: what JetBrains and the Java platform have said in public up to 2025. Plans change, so read these as direction, not promise.

Where a speed is given without a measurement it is an estimate from how Astra's VM works today: a value is 16 bytes (a kind and an 8-byte payload), a list holds such values, an object's fields and methods are found by name in hash tables, and arithmetic on two ints is one instruction with a type test.

Already settled, and not repeated below: generic types kept when running (5.7), function types of any number of parameters, interfaces with default methods, == comparing lists and maps by content (D14), strings counted by character (D4), static { } blocks instead of companion objects, and no final (5.7). Things that exist only for Java callers (@JvmOverloads, @JvmStatic, @JvmName, @Throws, getX()/setX() names, platform types String!) have no counterpart to decide.

L0 One 64-bit integer type, or several sizes

The question. Whether Astra keeps one integer type, int, 64 bits and signed (as now), or has several sizes as Kotlin does.

Kotlin, and why. Byte (8 bits), Short (16), Int (32) and Long (64), the JVM's primitives, which Java took from C. In 1995 32-bit arithmetic was what the hardware did fastest, and an array of 32-bit ints took half the memory of 64-bit ones. Int is the default: a literal is an Int, a Long needs an L after it, nothing widens by itself, and an Int wraps past about 2.1 billion. That is why milliseconds, nanoseconds and file sizes have to be Long.

Others.

  • Python and Ruby: one integer type with no size limit.
  • JavaScript: one number type, a double, exact for integers up to 253; BigInt is separate.
  • Lua (from 5.3) and Dart: one 64-bit integer type beside the float.
  • Swift: Int is 64 bits on 64-bit machines, with Int8 to Int64 beside it. Apple's advice is to use Int everywhere unless a size is needed for storage or a file format.
  • Go: int is 64 bits on 64-bit machines, with int8 to int64 and the unsigned sizes; every conversion is written.
  • Rust: i8 to i128; an unmarked literal is an i32; every conversion is written.
  • C# and Java: int is 32 bits and long 64, with byte and short; an int widens to a long by itself.

If (d), four questions come with it.

  • Range. 0 to 255, as the items of bytes already are (D15), or Kotlin's -128 to 127. Suggested: 0 to 255, so a byte means the same everywhere; ported code that tests a byte's sign is rewritten, as D15 already says.
  • Arithmetic. a + b on two bytes gives an int (Kotlin, Java, C#), or a byte that wraps or traps (Go wraps, Rust traps). Suggested: an int, so that adding bytes never loses anything; storing the result back into a byte is a conversion written out.
  • Converting. n.toByte() keeps the low 8 bits, as Kotlin's does, or is an error past 255. Suggested: an error past the range, matching L4's trap, with n.toByteWrapped() (or n and 0xFF) for keeping the low 8 bits on purpose. A literal that fits (val b : byte = 200) needs no conversion.

What Kotlin intends, given the technology. Nothing announced. Byte, Short, Int and Long are fixed by the JVM and by every line of Kotlin and Java in use, and no change is proposed.

Recommendation

(a) and (d) are both sound. (d), with the suggested answers to its four questions, fits with bytes and D15, costs nothing on int arithmetic, and gives binary data a type, so it is a good choice; I would take it over (a). If L1's packed lists are built later, (c) can add storage sizes on top of either. With 64-bit ints, L4's overflow trap would almost never fire on correct code.

Decided2026-10-14: (d), byte and int only. Added 2026-10-15: uint16(at) and uint32(at) read unsigned values as an int (0 to 65,535 and 0 to 4,294,967,295), with their put forms, so no unsigned type is needed for them. A byte holds 0 to 255; byte arithmetic gives an int; n.toByte() is an error past the range, with toByteWrapped() or n and 0xFF for the low 8 bits; a literal that fits needs no conversion; a byte is a kind of value of its own when the program runs. Changed 2026-10-17 by R12 of the review: int16, int32, uint16, uint32 and float32 join byte as storage types, read as int or float, arithmetic staying 64-bit.

L1 Numbers in collections: plain, or packed

The question. How a list<int> or list<float> stores its numbers.

Kotlin, and why. On the JVM generics hold only objects, so a List<Int> holds boxed Integer objects, 16 or more bytes each plus a pointer. For speed Kotlin adds a second family: IntArray, DoubleArray and the rest, fixed in size, holding plain numbers.

Others.

  • C#: keeps generic types when running and makes a separate version of List<int> that holds plain ints. One list type, packed automatically.
  • Swift, Rust, Go: [Int], Vec<i32>, []int hold plain numbers. They are compiled to machine code per element type.
  • Java: like Kotlin, int[] beside List<Integer>.
  • Python: lists of objects, with array and numpy for packed numbers.
  • JavaScript: one array type, which the engines quietly pack when it holds only small integers or only doubles; Int32Array, Float64Array and the rest for explicit packing.

Options.

GainLoseRun speed
a. As now: every list holds 16-byte valuesNothing to build.Twice the memory for numbers.Unchanged.
b. Separate packed types (ints, floats, like bytes)Half the memory; faster numeric loops where used.Two kinds of list to choose between, with conversions; ported IntArray code maps onto them, ported List<Int> does not.Faster only where the program chooses them.
c. Packed automatically: a list<int> or list<float> stores 8-byte numbers, because it knows its item typeHalf the memory and better cache use for every number list, with nothing for the program to choose.The VM's list gets two ways of storing items, and every list operation chooses between them.Faster for number lists (memory traffic halved). Other lists pay one test per access, about 1 to 2%.

What Kotlin intends, given the technology. Waiting on the JVM. Java's Project Valhalla is to let a List<int>-like generic hold plain numbers (its later "specialised generics" phase), and Kotlin has said its value classes are designed to map onto Valhalla when it arrives. Until then Kotlin keeps IntArray and its kind beside its lists. Valhalla's first part (value classes, in preview) does not yet include this.

Recommendation

(a) now, and (c) later, measured. Keeping the types when running is what makes (c) possible. The 3D view (M11) and large tables are where it would show.

Decided2026-10-14: (c), packed automatically, for every list whose items are values: list<int>, list<float>, list<char>, list<byte>, list<bool> and lists of value types (L2) store their items one after another at their own widths, because the list knows its item type. bytes is list<byte>. A list of objects, of any, of number or of a nullable type stores values as now. There is one sequence type: a separate pack<T>, considered the same day, was merged into the list. Design: value-lists.html.

L2 Value types: small objects without a heap allocation

The question. Whether small objects such as Point, Dimension, Color, Insets and Rectangle can be values, copied where they are used, instead of objects made on the heap and pointed to.

What an object costs today. Point(1, 2) is two allocations: the object (about 56 bytes: the header the collector needs, its class, and a table for its fields) and the table's entries (4 entries of 24 bytes, since fields are found by name). About 170 bytes with the allocator's own overhead, for 16 bytes of numbers. Each is linked into the collector's list and visited at every collection. Jade makes many: every sizes() gives a Sizes of three Dimension objects, every component has a Rectangle for its bounds, and drawing passes Color and Point objects about.

Two different savings. Much of that cost is the field table, not the allocation. With static types an object's fields can sit at fixed places (planned for part 4 of M6.5, "member access by position"), which takes a Point to one allocation of about 90 bytes, for every class and without any new kind of type. Value types go further, to no allocation at all.

What changes in meaning. A value is copied when assigned or passed. If its fields could change, b = a; b.x = 5 would leave a alone, and list[0].x = 5 would change a copy that is then thrown away, which is C#'s best-known trap with mutable structs. So value types are best immutable (only val fields): then copying cannot be seen, and a value behaves exactly as an immutable data object, except that it has no identity (=== means nothing; == compares contents).

Kotlin, and why. value class may wrap a single field, because the JVM has no user-defined value types. Project Valhalla, which would add them, is still unfinished after ten years.

Others.

  • C#: struct, any number of fields, stored inline and copied on assignment; mutable, with the trap above. Its guidance is to keep structs to about 16 bytes, since copying larger ones costs more than the allocation saved.
  • Swift: struct is the default for small types; mutation is allowed only on a var, through methods marked mutating, which makes copies visible in the code. Its collections are structs too, copied only when changed.
  • Rust and Go: every type is a value unless placed behind a pointer.
  • Java: record gives content equality but is still a heap object with identity; Valhalla's value classes are in preview.
  • Python and JavaScript: none; small objects are heap objects (Python's __slots__ and JavaScript engines' hidden classes give the fixed-place saving above).

The difficulty in Astra. A value in a variable, a field or a list is 16 bytes: a kind and 8 bytes of payload. A value type larger than 8 bytes (a Point of two 64-bit ints is 16) does not fit, so it needs either slots of more than one width in frames, objects and lists, as the JVM does for long and double, or to be boxed after all.

a. None: classes and data classes onlyNothing to build.Every small object is allocated and collected.As now; much better once fields sit at fixed places (part 4), which is planned either way.

What Kotlin intends, given the technology. Mostly what Astra has decided, once the JVM can. JetBrains' published design notes for value classes describe classes with several fields, stored flat with no allocation, when Valhalla provides them, and discuss a way to write a change to one property of an immutable value that makes a changed copy, the idea behind L2's pts[i].x = 4. Valhalla's value classes (JEP 401, in preview) also store arrays of values flat, as L1 and L2 do for lists. None of this has shipped in Kotlin yet.

Recommendation

(b) when convenient, since it costs little and keeps the way open. First build the fixed field places of part 4, which every class gains from, then count allocations in a Jade frame. If small objects still cost much after that, (c) for the one-number types such as Color, and (d) only if Point and Rectangle remain the cost. Not in M6.5.

Milestone M6.6.

L3 Unsigned integers

The question. Whether to have unsigned integer types beside int.

Kotlin, and why. UInt, ULong and the rest, added late (stable in 1.5) as wrappers over signed ints, because the JVM has none.

Others. C, C++, Rust, Go, Swift and C# have unsigned types natively. Java has none and offers helper methods (Integer.toUnsignedString, >>>). Python's integers have no size; JavaScript has one number type and the >>> operator.

Options.

GainLoseRun speed
a. None, plus a logical shift >>> and helpers such as toUnsignedStringOne integer type; no mixing rules.Code that needs unsigned 64-bit arithmetic writes it by hand. Rare outside hashing and binary formats, and Astra's binary formats are read in C++.Unchanged.
b. Unsigned typesPorted UInt code reads the same.Mixing rules for every operator; more conversions to write; a bigger checker.Unchanged per operation.

What Kotlin intends, given the technology. Done: UInt, ULong, UByte and UShort became stable in Kotlin 1.5, as wrappers over the signed types. Nothing further is announced.

Recommendation

(a). bytes already covers 0 to 255.

Decided2026-10-14: no unsigned integer types. int stays signed, 64 bits; byte (0 to 255, L0) is the one unsigned type. Data that wants unsigned values uses byte and bytes. Whether to add the logical shift >>> and helpers such as toUnsignedString is L22. Reconsidered 2026-10-15 and kept: the code being ported has no unsigned types; its nine toUInt() calls read 32-bit values that Astra's int holds whole, now read with uint32(at) (L0), and its 68 ushr calls are L22's >>>. Changed 2026-10-17 by R12 of the review: int16, int32, uint16, uint32 and float32 join byte as storage types, read as int or float, arithmetic staying 64-bit.

L4 Integer overflow

The question. What happens when an int operation goes past the 64-bit range. Today Astra wraps silently, as Kotlin does.

Kotlin, and why. Wraps silently, as the JVM does, and as C and Java did before it, because checking costs a little on every operation.

Others.

  • Java, Kotlin, Go: wrap. C#: wraps by default, with a checked context that traps.
  • Swift: traps, so the program stops with an error, and offers &+ for wrapping on purpose.
  • Rust: traps in debug builds and wraps in release builds, with wrapping_add, checked_add and saturating_add to say which is meant.
  • Python: integers grow without limit.
  • JavaScript: numbers are doubles and lose precision past 2^53 (BigInt is separate).
  • C: signed overflow is undefined behaviour.

Options.

GainLoseRun speed
a. Wrap (as now)Fastest; the same as Kotlin, so ported hashing code behaves the same.A wrong result in silence.Unchanged.
b. Trap, with wrapping functions for code that wants it (a.wrappingPlus(b), or &+ as Swift)A wrong result becomes an error at the line that caused it.Ported code that wraps on purpose (hashes, random number generators) has to say so.One overflow test per +, -, * on ints: an estimated 2 to 5% on integer-heavy loops, less elsewhere. To be measured.
c. Grow into big integersNever wrong.Every operation must be ready to change representation; big integers to build.Slower: an estimated 5 to 10% on integer arithmetic, more where numbers do grow.

What Kotlin intends, given the technology. Nothing announced. Kotlin wraps silently, as Java does; checked arithmetic is available only by calling Java's Math.addExact and the like.

Recommendation

(b). 64-bit overflow is rare, so when it happens it is almost always a bug, and an error at the line is worth a few percent on arithmetic. Hash functions in the standard library would use the wrapping form.

Decided2026-10-14: (b), trap. An int operation (+, -, *, and the like) whose result does not fit in 64 bits is an error at that line, not a wrapped number. Code that wants wrapping (hashes, random number generators) says so with Swift's operators: a &+ b, a &- b and a &* b wrap past 64 bits instead of failing. Each is one symbol, so a & +b (a bitwise and with a unary plus) needs its space, as in Swift. The cost, an estimated 2 to 5% on integer-heavy loops, is to be measured when it is built.

L5 A lambda where an interface with one method is expected

The question. Whether button.onClick { ... } can pass a lambda where the parameter's type is an interface with a single method.

Kotlin, and why. Only for interfaces marked fun interface (Kotlin 1.4), and for Java's single-method interfaces, which Java code uses everywhere for callbacks.

Others. Java converts a lambda to any interface with one abstract method. C# keeps delegates (function types) and interfaces apart, with no conversion. Swift does the same with closures and protocols. TypeScript's structural types let an object with a call signature be used directly.

Options.

a. No conversion: callbacks are function typesSimplest.Ported code that declares fun interface has to become function types.Unchanged.
b. Kotlin's fun interfacePorted code is unchanged; the type has a name and can gain default methods.A little checker work.One small object made per conversion, so a call through it is about as fast as a method call.

Recommendation

(b), for porting. JadeUI mostly uses function types already, so it matters little either way.

Decided2026-10-14: any interface with exactly one abstract method takes a lambda, as in Java, whatever default methods it has besides; no marker is needed. Kotlin's fun interface is not part of Astra: a ported one is written interface. (Kotlin required the marker because adding a second abstract method to a library's interface would silently break the lambdas written for it elsewhere; Astra compiles the whole program, so that change shows up as compile errors at those lambdas.) Where a call could take the lambda as either of two such interfaces, through overloads, it is a compile error until the lambda says which.

L6 Tail calls

The question. Whether a call that is the last thing a function does reuses the function's frame, so deep recursion cannot run out of stack.

Kotlin, and why. Only tailrec fun, where a function calling itself in tail position is turned into a loop. The JVM cannot do general tail calls.

Others.

  • Scheme and Lua guarantee all tail calls; Erlang and Elixir rely on them for loops.
  • Scala (@tailrec) and Clojure (recur) do self-recursion only, as Kotlin.
  • JavaScript's standard requires them, but only Safari implements it.
  • Python refuses, so that every call stays in error tracebacks.
  • Java, C#, Go and Rust make no promise.

a. NoneEvery call appears in an error's trace.Deep recursion ends in "stack overflow".Unchanged.

c. All tail callsRecursion of any shape is safe.Calls vanish from error traces, which makes errors harder to follow.About the same as a call.

What Kotlin intends, given the technology. Nothing announced. The JVM has no plan for general tail calls (Project Loom, which brought virtual threads, did not add them), so Kotlin keeps tailrec for a function calling itself.

Recommendation

(b).

Decided2026-10-14: automatic, with tail as an optional check, as Scala does with its @tailrec. L10 A character type

In detail. The question. (From M6.5 part 3, when the built-ins were declared.) stock["apples"]-- reads a map by key, which gives int?: the key may not be there. What may ++, --, +=, -=, *=, /= and %= do with a place that may be null: a map entry, a field of type int?, list.getOrNull(i)?

Today. The checker reports ++ and -- on such a place but lets += through; when it runs, a missing key fails either way (unsupported operand types for '-': null and int). a?.visits++ is already allowed: it does nothing when a is null.

Decided2026-10-17, the user: (d), null-safe operators, and a start value written in the index. stock["apples"]--?, stock["pears"] +=? 2, maybe.count++? and a?.visits++? change the place when it holds a value and do nothing when it is null or the key is missing. The whole family has the form: ++? --? +=? -=? *=? /=? %=?. They are statements, as ++ is, so a ? after ++ cannot be read as the start of ? :; +=? is one token. The plain operators on a place that may be null are a compile error that says why and what to write: "stock["apples"] may be missing, so -- cannot change it; use --? to skip it when missing, stock["apples", default = 0] to start it from a value, or ?:". The ? form on a place that cannot be null is an error too ("count is an int, never null; use ++"), so the ? always means something. Where a missing key should start from a value, the value is written in the index, beside the key it belongs to, as Swift does: counts[word, default = 0]++, totals[name, default = 0.0] += price, groups[kind, default = []] += [item]. It works with every operator and as a read: counts[word, default = 0] gives the value, or 0 when the key is missing, without adding it, and its type is the map's value type, never null. It is a named argument of a map's index, so grid[x, y] and the like are unaffected; an update through it is one lookup, finding the entry or making it. For a change that is not one operator, map.update(key, start) { old -> new } gives the new value: scores.update(name, 0) { it * 2 + 1 }. No increment helper: the index says it. update is in the standard library now; the operators, the index's default and their errors come in M6.5 part 3, with the rule that everything is typed. (D158)
